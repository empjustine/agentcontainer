# d027 — Path-prefix peer routing

## Problem

Peer mode meant "shove everything at
`https://bazzite…/<uuid>/v1` and hope for the best": the coding-agent
generators emitted `<peerBase>/v1` baseUrls and `<providerId>/<modelId>`
model ids, and llama-swap's peer machinery did the rest — parse the `model`
field, match the configured peer, swap in its upstream **and its API key**.
That coupling had three costs:

- **The router had to "know" models.** Adding or renaming a provider meant
  regenerating llama-swap's peer table server-side (`gen-lib.mjs`'s
  `PROVIDERS`), and clients had to speak llama-swap's id dialect
  (`cline-pass/cline-pass/<model>` double prefixes, `:free` scoping, …).
- **Provider dialects were flattened.** llama-swap's peer surface is
  OpenAI-completions-shaped, so providers whose native wire format differs
  could not be peer-routed at all: Google (native `google-generative-ai`
  paths — `generate.sh` explicitly carried a "NO google layer" note) and
  Mistral's non-completions endpoints (`mistral-conversations`) silently
  stayed direct-only.
- **Auth was inverted.** Clients authenticated to llama-swap with
  `PEER_API_KEY`; the router injected the provider's real key. Two key
  systems, one of them meaningless outside the gateway.

## Change

Cloud peer routing moves to **llm-reverse-proxy**, the dumb, faithful
reverse proxy (path-prefix routing, byte-for-byte forwarding, no credential
handling — see `llm-reverse-proxy/README.md`). llama-swap keeps exactly one
job: swapping local GGUFs on the GPU host.

One peer base URL, one funnel front: the tailscale funnel serves the whole
`<peerBase>` route to **llm-reverse-proxy on host port 8080**, which
path-prefix routes everything behind it:

| Path under `<peerBase>` | Backend | Routing |
|---|---|---|
| `/<providerId>` | cloud providers | path prefix → provider's FULL real base URL |
| `/llama-swap/…` | llama-swap (LAN **8101**, via `http://127.0.0.1:8101`) | model-id magic, LOCAL GGUF only |

The port conflict this settles: llama-swap historically held host port 8080
and the funnel path-dispatched `/v1` → llama-swap :8080, `/<providerId>` →
:8101 at the tailscale-serve level. Funneling the WHOLE route to the proxy
(one dispatch instead of per-path tailscale-serve entries, one owner of the
funnel front) requires the proxy on 8080 — so llama-swap moves to 8101 and
becomes just another path-prefix route of the proxy (`"llama-swap":
"http://127.0.0.1:8101"` in the deployed config, generated by
`generate-config.mjs`). The loopback upstream means the containerized proxy
must run with host networking (llm-reverse-proxy/run.sh), and llama-swap's
`/v1` OpenAI surface is unchanged behind the `/llama-swap/` prefix — a
client route is now `<peerBase>/llama-swap/v1`.

### The client convention

Every cloud provider's peer route is
**`peerProviderUrl(peerBase, id)` = `<peerBase>/<id>`** (lib/peer-probe.mjs;
e.g. peer-mode hyper is `https://bazzite…/<uuid>/hyper`). The deployed
`llm-reverse-proxy.json` maps each provider id to the provider's **full
real base URL** — the same `baseUrl` facts as lib/cloud-providers.mjs:

```jsonc
{ "hyper": "https://hyper.charm.land/v1",
  "google": "https://generativelanguage.googleapis.com/v1beta", … }
```

The proxy strips the leading `/<providerId>` and single-joins the rest onto
that base, so `<peerBase>/hyper/chat/completions` hits
`https://hyper.charm.land/v1/chat/completions` and
`<peerBase>/google/models/…` carries Google's native dialect untouched.
`llm-reverse-proxy/generate-config.mjs` emits this config from the fact
table (and flags drift against an existing deployed config), so the two
sides cannot diverge silently.

Consequences, per generator family:

- **pi-native providers** (`generate-cloud-pi-native-providers.mjs`): the
  cascade probes the provider's own endpoint first (unchanged); when that is
  unreachable it probes the provider's **own peer path-route** — not a
  shared catalog — and emits the reroute-only override with `baseUrl` =
  `<peerBase>/<id>` and **no `apiKey`**: the proxy forwards credentials
  untouched, so pi's built-in per-provider auth (env key / OAuth) now flows
  to the provider directly. The `"$PEER_API_KEY"` reference is gone from
  cloud layers (it remains only on the local llama-swap layer, where it is
  llama-swap's own bearer). Model lists come from the provider's live
  listing under the route (bare provider-native ids — the `<id>/` prefixes
  of the llama-swap era are gone; `classifyCloud`-style id attribution is
  deleted), scoped by per-provider filters (openrouter `:free`, mistral
  non-embed/tts, google gemini-chat slice), with the vendored models.dev
  catalog as fallback when the route proves itself but cannot list (401
  without a key).
- **Alternative providers** (`generate-cloud-alternative-providers.mjs` —
  cline-pass, hyper): peer mode now emits the **same full block as direct
  mode** with one difference — `baseUrl` = `<peerBase>/<id>`; `apiKey`
  stays the provider's own `$<envKey>` reference (forwarded untouched by
  the proxy), and the lineup is the same models.dev catalog (the llama-swap
  listing-matching machinery is gone — the proxy does not gate ids).
- **opencode** (`generate-opencode.jsonc.mjs`): same per-provider
  path-route cascade; overrides carry the provider's real key env instead
  of `PEER_API_KEY`. The local llama-swap face keeps its `/v1` OpenAI
  surface and `PEER_API_KEY`, now behind the proxy's `/llama-swap` prefix
  (`<peerBase>/llama-swap/v1`).
- **`PEER_MODEL_FILTERS`** (both pi generators) replace the llama-swap-era
  server-side `filter` of the deleted `gen-lib` peer table: routing is per
  provider, so the client scopes its own override.

### Probe semantics (lib/peer-probe.mjs)

`probePeerRoute` / `probePeerRoutes(candidates, providerId, headers)`: a
route is **usable** when any http response other than a *dead-route status*
arrives — 401/403 credential gates included (the canonical "reachable ≠
authenticated" rule, docs/d022, now applied per route). Dead-route statuses
`404 / 502 / 504` mean the path does not deliver (funnel default-404,
proxy's unknown-provider problem detail, proxy→upstream leg failed/timed
out) and are never emitted. `fetchModelEntries` additionally normalizes
Google's `name: "models/<id>"` listing shape to `id`.

## What this enables

- **Google** joins the pi-native cascade (lib/cloud-providers.mjs,
  `PI_NATIVE_CLOUD_IDS`): its native generative-ai dialect forwards
  byte-for-byte under `<peerBase>/google`, something llama-swap's
  openai-completions surface could never do. When
  `generativelanguage.googleapis.com` is unreachable (wsl2), the override
  reroutes it through the peer while pi keeps its own provider logic and
  `GEMINI_API_KEY`.
- **Mistral** (already in the fact table) actually works end to end now:
  the reroute-only override carries no `api`, so pi keeps its
  `mistral-conversations` wire format and the proxy forwards those
  non-completions endpoints untouched.
- Adding a provider is now a **fact-table row** (`lib/cloud-providers.mjs`)
  plus, for pi, a merge-order row in merge-models-json.mjs's header — no
  serving-side peer table, no id dialect.

## Deployment (bazzite)

1. `cd llm-local-inference && ./generate.sh && ./run.sh` — llama-swap on
   LAN **8101** (`HOST_PORT` → in-container 8080).
2. `cd llm-reverse-proxy && ./build.sh && ./generate.sh &&
   ./run.sh` — the funnel front on LAN **8080**, host networking (no secrets
   needed — the proxy injects nothing; the generated `llama-swap` provider
   routes the local face back at `http://127.0.0.1:8101`).
3. The tailscale funnel serves the whole `<uuid>/` route to :8080 — the
   proxy path-prefix routes `/<providerId>` to the cloud and `/llama-swap/`
   to the local instance. Until both are up, the peer path-routes probe as
   dead (404) and every generator correctly keeps direct/built-in routing —
   the migration is safe to roll out generator-first (verified: the funnel
   404s every unknown prefix; probes reject them).

## Committed artifacts

The committed `coding-agent/models.json`, `model-0*.json` and
`opencode.jsonc` ARE host-specific snapshots (SKIP_GEN fallbacks),
regenerated by `generate.sh` on each target host — the generators are the
source of truth, and on any host that can reach the funnel (or a stand-in)
a plain rerun re-emits the shape below; probes that find nothing correctly
leave the files untouched rather than writing garbage.

The checked-in snapshots have been brought to this shape once, offline:
`llama-swap` → `<peerBase>/llama-swap/v1` (its own `/v1` face behind the
proxy prefix, `$PEER_API_KEY` still llama-swap's bearer), pi-native cloud
overrides → reroute-only `<peerBase>/<providerId>` (no `apiKey`/`api`/
`compat` — pi's built-in per-provider auth and dialect), openrouter-family
model ids unprefixed, cline-pass ids left in their catalog-native
`cline-pass/<id>` form (what models.dev serves and the alternative
generator re-emits verbatim), `models.json` re-merged from the layers.
The next `generate.sh` run on a deployed host remains the authoritative
refresh — it re-probes live model lists, which no offline conversion can.
