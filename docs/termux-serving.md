# Termux / a50 serving environment

This documents the **termux** variant of the llama-swap serving layer
(`openai-completions/`) — a no-container build for resource-constrained
hosts running Termux (e.g. the **a50** phone/router environment).

## What it is

A phone/router cannot run the containerized llama-swap (`openai-completions/`)
image (no usable podman/docker for container-shaped amd64 images, no local
llama.cpp inference). Instead this variant ships a **native Termux build of
llama-swap** compiled for Android arm64, plus the capability-gated config
generator, which produces a **peers-only** llama-swap config here (cloud
providers proxied through llama-swap, no local GGUF serving) — no container
backend and no GPU are detected, so the local layer is never emitted.

The generators (`generate-general.yaml.js` + the two `generate-peer-*.yaml.js`)
are **peers-only by construction** — they emit cloud-provider peers and never a
local `models` section (local llama.cpp inference is impossible on a
phone/router):

| Mode | Local models | Cloud peers | Used by |
|------|-------------|-------------|---------|
| (peers-only, always) | ✗ (empty `models` section) | ✓ | termux/a50, OCI free tier |

## Files

| File | Role |
|------|------|
| `build.sh` | Dual-mode build: on Termux (termux `$PREFIX` = `/data/data/com.termux/files` exists) builds the native android/arm64 llama-swap binary into `~/ls-build/llama-swap-termux` (clones `~/llama-swap` if needed); everywhere else it pre-pulls the container image `run.sh` will use (unified-vulkan / :cpu per the generated config.d, `LLAMA_SWAP_IMAGE` override). |
| `generate.sh` | Generates the split `config.d/` by running the three generators below. Run this to refresh peer lists. |
| `run.sh` | Containerized multipurpose instance: launches the llama-swap container with `-config-dir config.d/`. Used on bazzite/OCI-style hosts. |
| `run-native.sh` | Native serve only (Termux): execs the native llama-swap binary with `-config-dir config.d/`. Errors clearly if the binary or `config.d/` is missing (run `build.sh` / `generate.sh` first). |
| `gen-lib.mjs` | Shared generator helpers (provider defs, fetch, yaml writing). |
| `generate-general.yaml.js` | Writes `config.d/00-general.yaml` (globals + ctxWindows) from `llama-swap-core.json`. No network. |
| `generate-peer-cloud.yaml.js` | Writes `config.d/peer-cloud.yaml` (`peers.openrouter`, `peers.opencode`, `peers.opencode-go`). OpenCode Zen/Go model ids come from the vendored models.dev catalog (ALL models, unfiltered); OpenRouter from its live `/models` (`:free` slice). |
| `generate-gfx1030-models.mjs` | Probes a live gfx1030 local-inference instance (PEER_BASE_URL, then the bazzite tailscale URL — localhost candidates are deprecated, the legacy :18080 port is gone) and writes `config.d/22-peer-gfx1030.yaml` (`peers.gfx1030`). |
| `config.d/` | Generated split llama-swap config (checked in as a starting point; regenerated by `generate.sh`). Loaded by llama-swap with `-config-dir`. See [d018-split-config-d.md](d018-split-config-d.md). |

See also: [environments-and-peer-variants.md](environments-and-peer-variants.md),
`openai-completions/generate-local-llm-models.yaml.js` (emits
`config.d/10-local-llm-inference.yaml` local GGUF model args on GPU-capable
hosts; llama-server resolves weights from HF at runtime — no models-local/
fallback).

## Env vars

### Provider keys & base URLs

Provider keys are read as plain environment variables by the generators
(e.g. `OPENROUTER_API_KEY`, `OPENCODE_API_KEY`). The old `__`-prefixed
convention is deprecated and must not be used. OpenCode uses a single unified
`OPENCODE_API_KEY` for both the Zen and Go peers — there is no longer a
Zen/Go-split or `__`-prefixed key name (and the base URLs are hardcoded, not
env-overridable).

| Provider | API key env | Default URL |
|----------|-------------|-------------|
| OpenRouter (free) | `OPENROUTER_API_KEY` | `https://openrouter.ai/api/v1` |
| OpenCode (Zen + Go) | `OPENCODE_API_KEY` | zen: `https://opencode.ai/zen/v1` · go: `https://opencode.ai/zen/go/v1` |

### Serving config

All of these live in `.env` (see the committed `.env.example`); there is no
separate shell config file. Paths such as the build output, the source
checkout, and the `config.d/` location are fixed conventions derived from each
script's own directory — they are **not** user-configurable.

| Var | Default | Description |
|-----|---------|-------------|
| `LISTEN` | `:8080` | Listen address for the llama-swap server (`run-native.sh` reads it from `.env`). |
| `LLAMASWAP_API_KEY` | *(none)* | Auth key that pi (the client) must send to llama-swap. |

(The provider keys in the table above — `OPENROUTER_API_KEY`, `OPENCODE_API_KEY` — are likewise read from `.env` by the generators.)

## Native build (Termux branch of build.sh)

On Termux, `build.sh` builds the binary into `~/ls-build/llama-swap-termux`
(cloning `~/llama-swap` if needed) — the same steps `run-native.sh`'s missing-
binary error points at:

```
LLAMA_SWAP_BIN="$HOME/ls-build/llama-swap-termux"
LLAMA_SWAP_SRC="$HOME/llama-swap"
[ ! -d "$LLAMA_SWAP_SRC" ] && git clone https://github.com/mostlygeek/llama-swap.git "$LLAMA_SWAP_SRC"
CGO_ENABLED=0 GOOS=android GOARCH=arm64 GOGC=50 go build -p=2 -trimpath -ldflags="-s -w" -o "$LLAMA_SWAP_BIN" "$LLAMA_SWAP_SRC"
```

`GOOS=android` (not `linux`) is critical on Termux: an android-targeted binary
uses Android's system DNS resolver instead of the missing `/etc/resolv.conf`.
A linux-targeted binary would fall back to `localhost:53`, which fails.

## Retired: the PRoot sandbox path (run-proot.sh)

`run-proot.sh` used to confine the native llama-swap binary inside a basic
PRoot sandbox (`proot_run()` in `container-tool.sh`), as a termux analog of the
container sandbox. It was **removed along with the PRoot backend**: PRoot is
ptrace-based path translation — no kernel namespaces, no cgroups, no real
root, no GPU passthrough, no read-only binds — so it provided the appearance
of sandboxing without the substance, and the native binary it wrapped talks to
the network directly anyway. On Termux, serve bare with `run-native.sh`; on
hosts that need stronger-than-container isolation, the qemu/libvirt option is
assessed in [d020-libvirt-qemu-sandbox.md](d020-libvirt-qemu-sandbox.md)
(not implemented).

## OCI peers-only env layout

For containerized OCI-style hosts (e.g. Oracle Always Free), the peers-only env
layout is the same as Termux's — use `openai-completions/.env.example` as
a template (it documents the plain, un-prefixed provider keys and `LISTEN`, with
no `LLAMACPP_BASE_URL` / `LLAMA_API_BASE_URL` since there is no local llama.cpp
server in peers-only mode).
