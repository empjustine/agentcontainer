# d018 — split llama-swap config (`config.d/`) per functionality

## Problem

Every serving dir (now squashed into the multipurpose `openai-completions/`;
previously `openai-completions-gfx1030` + `openai-completions-peer`, and the
archived `openai-completions-arm5/`) used to ship a single monolithic `config.yaml` produced by
code that had to cover a wide range of distinct use cases at once: local GGUF
inference, OpenRouter peers, OpenCode Zen peers, OpenCode Go peers, and all the
global settings / macros / ctxWindows. That forced a single, heavily-branched
generator and made the config brittle — one wrong model list or peer toggle
could break the whole file.

llama-swap supports loading **every** `*.yaml`/`*.yml` directly under a
directory via `-config-dir <dir>` (additive merge — see
`internal/config/merge.go`). We use that to split the monolith into small,
single-concern files — and, together with the capability-gated `generate.sh`
(the openai-completions analog of `coding-agent/generate.sh`), to make
`config.d/` contain exactly the layers that work on the current host.

## Layout

`openai-completions/config.d/` (single multipurpose dir; layers appear per host
capability — `generate.sh` also removes stale layers):

| File | Concern | Generated by | Needed on |
|------|---------|--------------|-----------|
| `00-general.yaml` | global settings + `macros` + `ctxWindows` (the "general purpose" config) | `generate-general.yaml.mjs` | all |
| `10-local-llm-inference.yaml` | local llama.cpp `models` map | `generate-local-llm-models.yaml.mjs` | GPU-capable container hosts only |
| `launch-gguf.sh` | HF-snapshot resolver for local GGUF launches (static, copied to `config.d/` by `generate.sh`) | — | GPU-capable container hosts only |
| `peer-cloud.yaml` | `peers.openrouter` + `peers.opencode` + `peers.opencode-go` + `peers.cline-pass` | `generate-peer-cloud.yaml.mjs` | whenever any provider answers |
| `22-peer-gfx1030.yaml` | `peers.gfx1030` (route to a remote local-inference instance) | `generate-gfx1030-models.mjs` | non-GPU hosts only |

The split is by **function**: one general-purpose file, one local-inference
file, and one generator **per peer family** — the cloud providers together
(`peer-cloud.yaml`; OpenCode Zen + Go share `OPENCODE_API_KEY`), and the
gfx1030 local-inference route on its own.

`generate-general.yaml.mjs` is a straight conversion of `llama-swap-core.json`
(no network). The two peer generators write only their own peer key:
`generate-peer-cloud.yaml.mjs` enumerates OpenCode Zen/Go model ids from the
**vendored models.dev catalog** (`models.dev.api.json`, ALL models,
unfiltered — the endpoint's own tier/availability filtering was unreliable and
silently hid models; access is decided at request time by the peer's key) and
OpenRouter's live `/models` (`:free` slice); ClinePass's ids also come from
the models.dev catalog (single OpenAI-compatible endpoint, one peer block for
every model — see `coding-agent/generate-cline-pass.mjs`'s header for why no
per-model API divergence). The catalog is refreshed
atomically on every `generate.sh` run by `refresh-models-dev.mjs` (tmp file +
validation + rename — a failed fetch never clobbers the last good copy). The
former `google` peer is GONE: Google AI Studio's special API shape does not
match llama-swap's OpenAI-compatible peer expectations and was never proxied
correctly (docs/d005 records the discovery work; google models reach the tree
via coding-agent's built-in provider instead).

### No shell in model `cmd` strings

llama-swap does **not** run model `cmd`s through a shell:
`internal/config/commands.go` (`SanitizeCommand`) splits the string with posix
shlex and execs argv[0] directly. Shell syntax (`$(...)`, variable assignment,
globs) therefore cannot appear inline in a `cmd:` value — llama-swap tries to
exec a binary literally named `SNAP=$(for`. Wrapping in `sh -c '...'` also
does not work here, because macro expansion happens textually before the
split, so the single quotes inside the sampling macros
(`--chat-template-kwargs '{...}'`) would break the wrapper quoting.

The dynamic HF-snapshot resolution (pick the first
`models--<org>--<repo>/snapshots/<hash>` containing both the GGUF and its
mmproj, normalize sharded GGUFs to their 00001 shard, append
`--model/--mmproj`, exec) lives in `config.d/launch-gguf.sh` instead.
Non-`.yaml` files under `-config-dir` are ignored by the merge loader, so the
script ships alongside the fragments and reaches the container through the
same read-only mount. The generated `cmd`s are plain argv:

```
sh /etc/llama-swap/config.d/launch-gguf.sh <repo-dir> <gguf> <mmproj|-> -- ${LLAMA_SERVER} ${family-macros} …
```

invoked via `sh` so no exec bit is required. The expanded `${LLAMA_SERVER}`
must directly follow the `--` separator: its first token (`llama-server`) is
the server binary, which the launcher resolves via `PATH` and then common
install dirs (`/usr/local/bin /usr/bin /bin /opt/llama.cpp/bin /app /app/bin`)
— image layouts differ across llama-swap unified-image revisions, and an
unresolvable bare argv[0] exits 127 without a usable hint; if the lookup fails
the launcher prints its PATH probe result and exits 127.

**Cache-miss download fallback:** if the GGUF/mmproj is not cached, the
launcher delegates to the server's own downloader (`--hf-repo <org>/<repo>
--hf-file <gguf>`, mirroring a naive `llama-server -hf`), which fetches into
the same hub-cache layout — so after one cold start the snapshot lookup takes
over. The mmproj is left to the server's repo auto-detection in that path.
The fallback is on by default (`HF_TOKEN` comes via `run.sh`); set
`LAUNCH_GGUF_DOWNLOAD=0` to make a cache miss a hard error instead (offline
hosts, surprise-bandwidth avoidance). The launcher honors `LAUNCH_GGUF_HUB`
to override the hub path for testing.

`generate-local-llm-models.yaml.mjs` (which builds the local GGUF `models` map
from `llamacpp-model-data.json`) is run by `openai-completions/generate.sh`
**only** on hosts with a container backend + GPU devices — local llama.cpp
models are served by the one multipurpose instance where the hardware allows
it. Everywhere else the instance is peers-only by construction: no
`10-local-llm-inference.yaml`, and the `22-peer-gfx1030.yaml` route covers
reaching a remote local-inference instance instead. (The old fixed-purpose
`-gfx1030` / `-peer` dirs are under `OLD/openai-completions-gfx1030/` and
`OLD/openai-completions-peer/`; the MikroTik `-arm5` runner lives at
`OLD/openai-completions-arm5/` — see
[OLD/docs/environments-arm5-routeros.md](../OLD/docs/environments-arm5-routeros.md)
for the row that used to live in the environments table.)

Each generator imports the folder's own `gen-lib.mjs` (self-contained, no
cross-dir imports) so the dir can be copied onto a host in isolation.

## Merge contract

`LoadConfigSources` concatenates the files in sorted filename order, then runs
the normal loader (env + macro substitution) on the merged document. The rules
that dictate the layout above:

- **Identity-keyed maps** (`models`, `peers`, `groups`, `profiles`,
  `selectors`, `matrix`, …) merge *additively* — distinct keys combine, a
  duplicate key across files is a **hard error**. Each generator therefore
  owns a disjoint set of keys (the numbers prefixing the filenames document
  the load order but are not required for correctness).
- **`apiKeys`** is a sequence and **concatenates** across files, so it lives in
  exactly one file (`00-general.yaml`) to avoid surprise duplication.
- **`macros`**, **`ctxWindows`**, and every **scalar global** (`logLevel`,
  `startPort`, …) must be defined in exactly one file. Shared scalars conflict
  on mismatch; shared macro/ctx keys would double-define an entity. Hence they
  live only in `00-general.yaml`.
- **`${env.VAR}`** is substituted **per file, at llama-swap load time**, so
  every referenced env var must be present in *llama-swap's* own environment
  (the container gets it from the forwarded environment; the router via
  `/container/envs`).
  An unset `${env.*}` aborts the whole config load — same contract as the old
  monolith.

Because macro substitution runs on the *merged* document, the `${LLAMA_SERVER}`
/ `${qwen36}` / `${k80v80}` / … references inside the local `models` `cmd`
strings resolve against the macros defined in `00-general.yaml`.

## Regenerating

```sh
# multipurpose dir (openai-completions): generate.sh detects the host's
# capabilities and emits only the layers that work there
cd openai-completions && ./generate.sh
#   internally runs, per capability:
#   node generate-general.yaml.mjs              # always
#   node generate-local-llm-models.yaml.mjs     # GPU-capable container hosts
#   node generate-peer-cloud.yaml.mjs           # when providers answer
#   node generate-gfx1030-models.mjs           # non-GPU hosts only
```

`run.sh` (container) and `build.sh` (termux-native build or image pull) + `run-native.sh` (Termux) launch
llama-swap with `-config-dir <path>/config.d`. The peer generators skip a
provider whose fetch fails or (for OpenCode Zen) whose key is absent, so a
single provider outage never blanks the rest of the config.

### Staleness policy

`config.d/` is generated to **mirror the current host**, so each layer has an
explicit stale-output rule:

| Layer | On failure / capability loss |
|-------|------------------------------|
| `00-general.yaml` | never stale (static source) |
| `10-local-llm-inference.yaml` + `launch-gguf.sh` | **removed** by `generate.sh` when the container backend or GPU devices disappear — serving local models without the hardware is a hard error at swap time |
| `peer-cloud.yaml` | **removed** when no provider answers AND the models.dev catalog lacks the OpenCode entries (write-or-remove is the generator's own contract); individual provider skips are granular, so one outage never blanks the others |
| `22-peer-gfx1030.yaml` | **kept** when the probe cascade finds no instance — a generation-time transient (tailscale blip, instance restarting) must not drop a working peer route; the file describes a *remote* host, not a local capability |

The asymmetry is deliberate: local layers describe *this* host (hard capability
ground truth), the cloud layer describes external reachability (cheap to
regenerate, safe to drop), and the gfx1030 layer describes a remote target
(transient detection failures must be tolerated).
