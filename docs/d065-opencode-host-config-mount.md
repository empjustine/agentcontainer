# d065 — opencode host config dir mount

**Status: active (landed).** `coding-agent/run.sh` no longer stages a per-run
copy of opencode's config. It mounts the host's real config dir
(`OPENCODE_CONFIG_DIR`, default `${XDG_CONFIG_HOME:-$HOME/.config}/opencode`)
RW and `generate.mjs` installs the generated `opencode.json` into that same
dir — mirroring what pi has done for its agent dir since docs/d054. Opencode's
DATA dir (`~/.local/share/opencode`: `auth.json`, `log/`,
`project/<slug>/storage`) stays on the per-run stage: it is the long-term
logs/sessions persistence, i.e. audit state (docs/d026), and opencode has no
session-dir knob to split it out.

## Problem

The opencode config was staged per run: `run.sh` copied the committed
`coding-agent/opencode.jsonc` into `$stage/opencode/config/opencode.json`
and mounted that fresh stage dir. That is exactly the arrangement docs/d054
removed for pi, for the same reasons:

- **Config garbage and a drift seam.** Every launch left a throwaway config
  copy under `~/workspace`, and the generator's output had TWO possible
  destinations (the committed `opencode.jsonc` that `run.sh` copies, or
  `$OPENCODE_CONFIG_DIR/opencode.json` only when the env var happened to be
  set at generate time) — so what the sandbox ran and what the generator
  refreshed could silently diverge.
- **The host opencode and the sandboxed opencode never shared config.** The
  host has a real opencode (mise-installed); a config dir that only exists
  per run means edits and installs never meet.

## Decisions

1. **`opencode_cfg_dir` is the host's real config dir, mounted permanent
   RW.** `run.sh` computes `$OPENCODE_CONFIG_DIR` else the XDG default —
   the same default opencode itself derives — and mounts it at
   `/home/$USER/.config/opencode`, with the in-container launch chain
   exporting `OPENCODE_CONFIG_DIR` at that path (unchanged from before; it
   now names the mounted host dir). The generator's install target, the host
   opencode, and the sandboxed opencode are one directory.
2. **The generator installs BOTH the host dir and the committed copy** —
   the pi pattern (docs/d054): `generate.mjs` generates into a SCRATCH copy
   of the committed overlay (the copy is also the d064 local stale-preserve
   input `previousLocalProvider` reads), and only a successful generation is
   installed: atomically-generated bytes are copied to
   `$ocHostDir/opencode.json` (pre-overwrite `.bak-<ts>` kept alongside,
   best-effort like the settings/models installs) and to the committed
   `coding-agent/opencode.jsonc` (warn-only on a read-only dir, like
   `refreshCommittedSnapshot`). A failed generation aborts the whole run
   (d063 fail-closed), touching neither copy.
3. **The committed `opencode.jsonc` stays, with a changed job.** It is no
   longer the runtime input `run.sh` copies; it is the reviewed git diff AND
   the next generation's stale-preserve input — so unlike pi's committed
   snapshot it refreshes on EVERY host that runs the stage, Termux included.
   There is deliberately **no SKIP_GEN install path** for opencode (pi's
   SKIP_GEN installs the committed `models.json`; opencode has no offline
   generation story and needs none).
4. **Partial opencode config is ACCEPTED at launch.** `run.sh` warns when
   `$opencode_cfg_dir/opencode.json` is missing and launches anyway —
   opencode runs fine on its built-in providers; a missing overlay only costs
   the peer reroute. This deliberately departs from pi's missing-artifact
   abort (exit 94): pi without `models.json` is broken, opencode without
   its overlay is merely un-rerouted. There is no fail-dead gate and no
   implicit regeneration (d041 still holds).
5. **The data dir stays per-run staged** (`$stage/opencode/data` →
   `~/.local/share/opencode`). It holds the long-term LLM logs (`log/`)
   and user sessions (`project/<slug>/storage`) — per-run audit state on
   the host (docs/d026), deliberately NOT the host's own
   `~/.local/share/opencode`. opencode exposes no data-dir env override
   (verified against 1.18.x: `OPENCODE_CONFIG_DIR` only moves config; data is
   pure XDG), so the mount at the default path IS the pin.

## Invariants and consequences

- **No credential gate is needed — by construction, cleaner than pi.**
  opencode's credential store (`auth.json`) lives in the DATA dir, which is
  never host-mounted; a host `auth.json` cannot leak into the sandbox, so
  d052's staging anti-goal holds without an abort (pi needed its exit-93
  `auth.json` gate only because its config dir is host-mounted and pi's own
  store lives there). Keys still resolve from the forwarded env
  (`workload_env` allowlist). The reverse flow — an in-container
  `opencode auth login` persisting a credential into the stage — is
  pre-existing behavior and unchanged.
- **Host config state is exposed to the sandbox** (e.g. `tui.json`, any
  operator files next to `opencode.json`). Accepted under d054's
  precedent; the credential-shaped risk is excluded by the data-dir split
  above.
- **Concurrency:** two simultaneous launches share one config dir (same
  accepted note as d054); session/log churn stays isolated per run.
- **Relabel cost:** each launch pays the `z,U` recursive relabel on the
  durable host config dir — tiny (one or two files), unlike the mirror-mount
  cost run.sh's comments warn about.
- **Termux is unchanged:** the opencode stage is still skipped there unless
  `OPENCODE_CONFIG_DIR` is set; run.sh is container-only (d059).
- **Consumers of the committed `opencode.jsonc` changed** —
  `run.sh` no longer copies it; `generate.mjs` seeds the stale-preserve
  from it and refreshes it. Retiring the file would break stale-preserve.

## Alternatives considered

- **Keep staging, only pin differently** — rejected for the d054 reasons
  (garbage + drift seam), which apply to opencode verbatim.
- **Fail-dead on a missing overlay (pi's exit 94)** — rejected: opencode on
  built-in providers is a usable sandbox; the operator's cost of a hard
  abort outweighs the missing peer reroute (operator decision, recorded
  here).
- **SKIP_GEN committed install** — rejected: no offline opencode generation
  story exists or is needed (see decision 3).
- **Mount the host data dir too** (full host-folder sharing) — rejected: it
  merges long-term log/session churn into the host's own XDG store and loses
  the per-run audit separation docs/d026 is built on.
- **Set `XDG_DATA_HOME` to the stage instead of mounting** — rejected:
  a mount is runtime-agnostic (works for any XDG-reading opencode version)
  and needs no in-container env beyond the existing pins.
